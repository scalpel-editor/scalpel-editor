# Phase 8 scrollbars plan

## Goal

Add compact in-window vertical and horizontal scrollbars around the Scintilla client. They expose the scroll state the retained editor core already owns, work with pointer and wheel input, preserve the existing tab and menu chrome, and remain a focused Phase 8 control rather than starting a general UI toolkit.

The vertical bar is present while Scintilla's vertical-scrollbar option is enabled. The horizontal bar is present while its option is enabled and wrapping is off, matching the retained Scintilla contract. Arrow buttons, overlay auto-hide, animated fading, touch dragging, markers in the track, configurable themes, and a minimap are out of scope.

## Current boundary and deficiencies

Scintilla already owns `topLine`, `xOffset`, vertical range calculation, the assumed horizontal `scrollWidth`, wrapping, and all clamping needed to keep a caret visible. It calls `ApplicationEditor::SetVerticalScrollPos`, `SetHorizontalScrollPos`, `ModifyScrollBars`, and `ReconfigureScrollBars`, but the host currently only records those calls in `ScrollState`. Nothing reserves side or bottom space, paints a bar, or turns a thumb position into a named editor scroll operation.

`ScrollState` mixes useful positions and vertical range values with callback counters kept only for tests. It has no horizontal range, page increment, visibility, or stable maximum-position definition. The scrollbar work should replace it with exact two-axis metrics and keep callback-count observations in tests instead of extending this production type.

The permanent-chrome path assumes one top band: `GetClientRectangle` subtracts only `topChromeInset`, `TopChromeRectangle` is the only chrome damage region, and the permanent painter runs only when damage intersects that band. Side and bottom bars need first-class rectangles without making every scroll invalidate or swap the whole frame.

Pointer routing currently gives modal cards priority, followed by the menu and tab strip, then the editor. Editor selection capture is already allowed to cross the top chrome. A thumb drag needs the matching rule in the other direction: after a press starts on a thumb, its motion and release stay with that thumb even outside the track, while an editor selection drag must not be stolen when it crosses a scrollbar. Wayland supplies the surface-level implicit grab until button release; the application needs only to retain which control owns that sequence and cancel it on a synthesized release, focus loss, or control removal.

Scintilla deliberately uses an assumed horizontal width instead of measuring the whole document. The current default is 2000 pixels and optional tracking only grows from measured visible lines. The application must expose that existing range accurately and must not add a whole-file measurement pass that would conflict with later oversized-file handling.

## Product behavior

- Use fixed 14-logical-pixel bars with a quiet opaque track, a higher-contrast thumb, hover and pressed states, a 24-logical-pixel minimum thumb when the track permits it, and a plain junction square when both bars are present. The renderer scales these logical dimensions through its existing framebuffer path.
- The editor client starts below the menu and tab bands, ends to the left of the vertical bar, and ends above the horizontal bar. The vertical bar begins below top chrome; the horizontal bar ends before the vertical bar. Very small windows clamp every rectangle and retain at least one logical client pixel where the frame permits it.
- Vertical metrics use Scintilla's display-line range, so folding and wrapping change the thumb without the chrome duplicating document-line calculations. Horizontal metrics use `scrollWidth` and the width of Scintilla's text rectangle, including the existing line-number margin behavior.
- A bar with no scrollable range paints a full-track disabled thumb and ignores thumb and track presses. Wrapping resets horizontal position and removes the horizontal bar; turning wrapping off restores the bar with a freshly clamped range.
- A left press on a thumb begins a drag without moving the caret or keyboard focus. The original pointer-to-thumb offset is retained, motion maps the available thumb travel to the complete editor range, and release ends the drag even when the pointer has left the track.
- A left press before or after the thumb moves once toward the press by the axis page increment: one visible vertical page minus one line, or one third of the visible horizontal page. The first slice has no press-and-hold repeat. Other buttons are consumed over scrollbar chrome and do not select text or request primary-selection paste.
- Wheel input over the vertical bar scrolls vertically and wheel input over the horizontal bar scrolls horizontally. Wheel input over editor content keeps the existing dominant-axis and Shift behavior. All wheel and scrollbar targets use the same upper-bound clamping, fixing the current ability of horizontal wheel input to move past the advertised assumed width.
- The pointer uses the arrow cursor over tracks, thumbs, and the junction. Hover changes repaint only the affected bar. Position changes repaint only the affected thumb region or bar; visibility and geometry changes repaint the complete frame because the editor client boundary moved.
- Modal file-error and unsaved-changes cards keep first input and overlay priority. An open menu remains above scrollbars. An active scrollbar drag owns motion and release before top chrome, while an active editor selection owns motion and release before scrollbar hit testing. Opening a menu or card, switching the active document, losing focus, resizing, changing scale, or losing the pointer device cancels a scrollbar drag cleanly.

## Ownership and rendering

Replace the current `ScrollState` with application-facing axis metrics containing position, upper bound, page size, page increment, and visibility. `ApplicationEditor` fills them from the existing Scintilla host callbacks and exposes narrow clamped vertical and horizontal scroll methods. Scintilla remains the only owner of `topLine`, `xOffset`, wrapping, folding, caret visibility, and scroll-width growth.

Add a focused `ScrollBar` component with Wayland-free axis layout, thumb mapping, hit testing, drag state transitions, and painting. Its model retains only hovered and dragged parts plus the drag offset; it does not own editor positions. Results are exact requests such as set vertical position or set horizontal position, which `main` applies through `ApplicationEditor`.

`ApplicationEditor` owns fixed client insets and the frame rectangles because Scintilla queries client geometry from the host. `ReconfigureScrollBars` recomputes vertical and horizontal visibility from the retained editor options and wrap state, then runs the normal size-change path only when those insets change. `ModifyScrollBars` updates both axis ranges, clamps a stale horizontal offset after a range shrink, and damages the affected bar without recursive reconfiguration.

Generalize permanent chrome from one top rectangle to the union of the top band, vertical bar, horizontal bar, and junction while retaining the one application-specific painter callback. `InvalidateTopChrome` remains narrow; add equally narrow scrollbar invalidation. Ordinary editor damage does not repaint the chrome, scrollbar position damage does not repaint the editor, and an overlay still forces a full-frame paint and full swap.

`main` owns one scrollbar interaction model and painter beside the menu and tab models. Its permanent painter draws menu, tabs, scrollbars, and the junction after Scintilla and before the menu or modal overlay. Pointer routing applies the ownership rules above and sets the Wayland cursor from the active modal, menu, scrollbar, top chrome, or editor state in that order.

## Commit sequence

1. **Expose exact editor scroll metrics.** Replace the production callback counters with vertical and horizontal axis metrics, calculate Scintilla-compatible upper bounds, page sizes, page increments, visibility, and maximum positions, and add narrow clamped vertical and horizontal scroll methods. Route existing wheel input through those methods and enable the retained visible-line width tracking without measuring the whole document. Extend `applicationHostTest` and `applicationInputTest`; build them and run `"production editor scrollbar metrics*"` and `"production editor pointer wheel*"`.
2. **Lay out, hit-test, and paint both bars.** Add the fixed dimensions, axis-neutral range-to-thumb mapping, minimum-thumb handling, disabled full-track state, vertical and horizontal rectangles, junction, hover and pressed paint, and overflow-safe arithmetic for large line counts. Keep the component independent of Wayland and editor internals. Add `scrollBarTest`; build it and run `"scroll bar layout*"`, `"scroll bar mapping*"`, and `"scroll bar paint*"`.
3. **Reserve side and bottom client space.** Make `ApplicationEditor` compute top, vertical, horizontal, junction, and editor-client rectangles; show vertical chrome when enabled and horizontal chrome only when enabled and not wrapping; generalize permanent-chrome damage detection; and keep tiny frames valid. Cover wrap transitions, resize, line counts, caret geometry, top-chrome coexistence, partial damage, overlays, and scaled framebuffer paint in `applicationHostTest`; run `"production editor scrollbar chrome*"` and `"production editor permanent chrome damage*"`.
4. **Connect host callbacks to scrollbar paint state.** Update both axis ranges and positions after load, edit, fold, wrap, resize, paint-driven width growth, caret scrolling, and document activation; clamp positions when a page grows or a range shrinks; and invalidate only the changed bar when geometry is stable. Verify independent tab scroll positions restore while the shared Scintilla assumed-width policy remains explicit. Build `applicationHostTest` and run `"production editor scrollbar updates*"` and `"production editor document scrollbar state*"`.
5. **Add pointer scrollbar interaction.** Implement hover, disabled rejection, single page-step track presses, thumb dragging with retained grab offset, wheel-over-axis behavior, drag cancellation, junction consumption, and the editor-selection-capture exception. Use Wayland's existing implicit surface grab rather than inventing an explicit capture request. Extend `scrollBarTest` and `applicationInputTest`; run `"scroll bar pointer*"` and `"production editor scrollbar input*"`.
6. **Integrate scrollbars with application chrome.** Paint bars with menu and tabs, establish input priority as file error, unsaved card, open menu, active scrollbar drag, top chrome, scrollbar hit, then editor, and keep cursor, IME, tab switching, portal and prompt transitions, resize, scale, pointer-device loss, and force close consistent. Add a headless workflow case spanning editor wheel scroll, thumb drag, tab switch, wrap change, modal suppression, and return to editor input; build the focused application targets and run `"scroll bar shell integration*"` and `"scroll bar workflow*"`.
7. **Complete the scrollbar workflow checks.** Update `ROADMAP.md` and ownership comments with the landed boundary, compile changed production headers alone, run `cmake --workflow --preset dev` because the change crosses editor geometry, rendering, input, and application chrome, build `scalpel-editor`, and perform a live Wayland check of both axes, thumb dragging, track paging, wrapping, resize, scaling, menus, tabs, and modal cards. Leave the full sanitizer matrix for the Phase 8 gate unless implementation uncovers a memory-lifetime reason to run one tree earlier.

## Completion checks

The work is complete when both axes reflect Scintilla's actual positions and ranges; folding, wrapping, resize, width growth, caret movement, and tab activation update the bars; wheel, track, and thumb input cannot overscroll or leak into editor selection; drag ownership survives leaving a track and is cancelled by lifecycle changes; top, side, bottom, junction, and overlay paint order is correct under partial damage and scaling; tiny windows remain valid; no whole-document width scan, external widget toolkit, or generic control framework has been introduced; changed production headers compile alone; and the normal development workflow passes.
